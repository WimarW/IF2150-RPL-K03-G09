# BAB 1: Deskripsi Umum

## 1.1 Deskripsi Umum Sistem
### 1.1.1 Ekspektasi Pengguna Terhadap Sistem
<p align="justify">Sistem ini melibatkan 3 aktor yang memiliki ekspektasi masing-masing yang berbeda.</p>
<ol>
    <li>Pelanggan: Sistem mampu menyelesaikan masalah yang sedang dialami. </li>
    <li>Pemberi Jasa: Sistem dapat memfasilitasi proses penjualan jasa mereka</li>
    <li>Layanan Pelanggan: Sistem mampu menunjukkan permasalahan yang dialami antar pelanggan dan pemberi jasa sehingga dapat menyelesaikan masalahnya</li>
</ol>

### 1.1.2 Alur kerja Sistem
<ol>
    <li>Pelanggan mengunggah/mendaftarkan informasi kebutuhan jasa ke perangkat lunak </li>
    <li>Aplikasi memberikan rekomendasi pemberi jasa relevan untuk kebutuhan pelanggan </li>
    <li>Pelanggan dan pemberi jasa melakukan negosiasi harga untuk pekerjaan yang ingin dilakukan</li>
    <li>Jika disetujui, pelanggan menginput persetujuan ke dalam aplikasi</li>
    <li>Pemilik jasa melakukan dan menyelesaikan pekerjaan fisik sesuai dengan persetujuan</li>
    <li>Setelah pekerjaan selesai, pelanggan akan melakukan pembayaran sebesar harga yang ditetapkan</li>
    <li>Proses diakhiri dengan kedua pihak saling memberi penilaian terkait kinerja pemberi jasa dan perilaku pelanggan</li>
</ol>

### 1.1.3 Harapan Penerapan Solusi
<p align="justify">Penerapan sistem ini diharapkan dapat menjaga standar kualitas dan profesionalisme penggunanya melalui sistem penilaian. Dengan sistem ini, pihak pelanggan dan pemberi jasa diwajibkan memberikan pelayanan dan perilaku yang terbaik untuk menjaga penilaian mereka. Sistem juga diharapkan dapat memberikan rasa aman dengan menyediakan lyananan ticket aduan apabila terdapat keluhan yang tidak bisa diselesaikan antara kedua belah pihak.</p>

## 2.3 Pemetaan Kebutuhan

Perhatikan kembali semua aktivitas yang telah didefinisikan pada tabel deskripsi aktivitas atau *activity diagram*. Jabarkan kebutuhan sistem yang akan dibuat dengan mengacu pada aktivitas-aktivitas tersebut. Setiap aktivitas (ID Aktivitas) dapat memiliki satu atau lebih kebutuhan yang berbeda. Pastikan untuk mengidentifikasi dan mengisi semua jenis kebutuhan yang relevan untuk setiap aktivitas, yaitu:

- **User Requirement**, yaitu kebutuhan dari sudut pandang pengguna (apa yang dapat dilakukan pengguna).
- **Business Requirement**, yaitu aturan, kebijakan, atau standar bisnis yang harus dipenuhi oleh sistem.
- **System Requirement**, yaitu kebutuhan yang menjelaskan apa yang harus dilakukan sistem dan bagaimana sistem harus bekerja dari segi performa, keamanan, keandalan, dsb.

Lengkapi juga dengan penjelasannya dan apakah keperluan tersebut perlu didukung oleh perangkat lunak atau tidak. Jenis kebutuhan tidak terbatas hanya dari tiga jenis di atas, dapat ditambahkan yang lain juga bila diperlukan, misalnya kebutuhan regulasi (*Legal*).

## 2.4 Kebutuhan Fungsional (KF)

| ID KF | ID Kebutuhan | Penjelasan |
| :--- | :--- | :--- |
| KF-01 |  | Sistem harus menyediakan form unggah ketersediaan jasa yang memungkinkan pelanggan mengisi deskripsi pekerjaan, kategori jasa, dan lokasi. |
| KF-03 |  | Ketika penyedia jasa mengirimkan form ketersediaan jasa, sistem harus menyimpan data tersebut ke dalam basis data dan menampilkan konfirmasi keberhasilan kepada pelanggan. |
| KF-04 |  | Sistem harus menyediakan halaman pendaftaran bagi penyedia jasa yang mencakup data diri dan jenis jasa yang ditawarkan. |
| KF-05 |  | Ketika pemberi jasa melakukan pendaftaran, sistem harus meminta izin akses GPS/lokasi bila izin ditolak, sistem harus menampilkan peringatan bahwa fitur pencarian berbasis lokasi tidak akan tersedia. |
| KF-06 |  | Ketika pemberi jasa mengaktifkan status aktif, sistem harus mencatat dan menyimpan titik koordinat lokasi pemberi jasa secara real-time ke dalam basis data. |
| KF-07 |  | Sistem harus menyediakan fitur chat antara pelanggan dan pemberi jasa untuk proses komunikasi dan negosiasi estimasi harga. |
| KF-08 |  | Selama sesi negosiasi berlangsung, sistem harus memastikan tidak ada pihak ketiga yang dapat mengakses atau ikut campur dalam percakapan antara pelanggan dan pemberi jasa. |
| KF-09 |  | Ketika pelanggan membuka profil pemberi jasa, sistem harus menampilkan informasi kontak alternatif (nomor telepon/WhatsApp) sebagai opsi komunikasi di luar platform. |
| KF-10 |  | Sistem harus menyediakan form bagi pelanggan untuk mengisi deskripsi rinci pekerjaan dan mengajukan penawaran harga awal kepada pemberi jasa. |
| KF-11 |  | Sistem harus memastikan pekerjaan hanya dapat dimulai ketika kedua belah pihak telah menyatakan persetujuan atas harga yang disepakati. |
| KF-12 |  | Ketika kedua belah pihak menyetujui harga, sistem harus mengunci detail pekerjaan dan nominal harga sehingga tidak dapat diubah tanpa memulai proses renegosiasi ulang. |
| KF-13 |  | Sistem harus menyediakan tombol konfirmasi penyelesaian pekerjaan bagi pemberi jasa, dan sistem harus mengirimkan notifikasi kepada pelanggan untuk segera melakukan pembayaran. |
| KF-14 |  | Bila pelanggan belum menyelesaikan pembayaran, sistem harus mencegah perubahan status pesanan menjadi "Selesai" dan menampilkan pengingat kewajiban pembayaran. |
| KF-15 |  | Ketika pembayaran berhasil dilakukan, sistem harus memperbarui status pesanan secara otomatis dan mencatat riwayat transaksi (waktu, pihak terlibat) ke dalam basis data. |
| KF-16 |  | Ketika status pesanan berubah menjadi "Selesai", sistem harus menyediakan form penilaian berupa rating bintang dan ulasan teks bagi pelanggan maupun pemberi jasa. |
| KF-17 |  | Sistem harus memastikan bahwa pelanggan dan pemberi jasa masing-masing hanya dapat memberikan satu penilaian per transaksi yang telah selesai. |
| KF-18 |  | Ketika penilaian baru diterima, sistem harus menghitung ulang dan memperbarui rata-rata rating profil pemberi jasa dan pelanggan secara otomatis. |

## 2.5 Kebutuhan Non-Fungsional (KNF)

| ID KNF | ID Kebutuhan | Parameter | Deskripsi Kebutuhan |
| :--- | :--- | :--- | :--- |
| *KNF01* | *R03* | *Reliability* | *Proses transaksi pembayaran harus memenuhi prinsip ACID untuk mencegah terjadinya data tersangkut (lost update) apabila terjadi kegagalan jaringan di tengah proses.* |
| *KNF02* | *R04* | *Security* | *Sistem harus mengenkripsi PIN atau password pengguna menggunakan algoritma SHA-256 sebelum data dikirimkan ke server, serta tidak menyimpannya dalam bentuk plain-text di database.* |
| *KNF03* | ... | *Security* | *Sistem harus memvalidasi input formulir oleh user pada sisi server untuk mencegah adanya serangan pada celah keamanan seperti SQL Injection* |
| *KNF04* | ... | *Response time* | *Validasi input user pada formulir harus tidak melebihi 2 detik dalam kondisi internet normal* |
| *KNF05* | ... | *Response time* | *Sistem harus dapat menampilkan daftar pemilik jasa dalam radius GPS dari pengguna jasa dalam waktu 2 detik* |
| *KNF06* | ... | *Reliability* | *GPS harus dapat ditampilkan dengan akurat pada pengguna jasa hingga < radius 50 meter* |
| *KNF07* | ... | *Security* | *Pesan yang dikirim harus dienkripsi dengan End-to-End Encryption* |
| *KNF08* | ... | *Response time* | *Pesan yang dikirim harus dapat sampai ke pihak yang menerima pesan dalam waktu 1 detik* |
| *KNF09* | ... | *Reliability* | *Sistem harus dapat menangani hingga 1000 percakapan serentak dari semua pengguna tanpa adanya masalah dalam komunikasi pesan* |

Silakan pilih yang relevan. Tidak perlu semua parameter menjadi kebutuhan non-fungsional. Berikut merupakan penjelasan dari setiap parameter. **Parameter dari Kebutuhan Non-Fungsional tidak terbatas hanya di bawah ini** karena hanya merupakan panduan sehingga dapat ditambah KNF yang lain, misalnya *constraint* dari sistem.

| Parameter | Penjelasan |
| :--- | :--- |
| *Availability* | Ketersediaan aplikasi, misalnya harus terus-menerus beroperasi 7 hari per minggu, 24 jam per hari tanpa gagal. |
| *Reliability* | Keandalan, misalnya tidak pernah boleh gagal (atau kegagalan yang ditolerir adalah …%) sehingga harus dipikirkan *fault tolerant architecture*. Biasanya hanya perlu untuk *critical application* yang jika gagal akan berakibat fatal. |
| *Ergonomy* | Kenyamanan pakai bagi pengguna. |
| *Portability* | Kemudahan untuk dibawa dan dioperasikan ke mesin/sistem operasi/*platform* yang lain. |
| *Memory* | Jika perhitungan kapasitas memori internal kritis (misalnya untuk P/L yang harus dijadikan *chips* dan ukurannya harus kecil). |
| *Response time* | Batasan waktu yang harus dipenuhi. Sangat penting untuk aplikasi *real time*. Contoh: "Aplikasi harus mampu menampilkan hasil dalam 4 detik", atau "ATM harus menarik kembali kartu yang tidak diambil dalam waktu 3 menit". |
| *Safety* | Yang menyangkut keselamatan manusia, misalnya untuk P/L yang dipakai pada sistem kontrol di pabrik. |
| *Security* | Aspek keamanan yang harus dipenuhi. |
